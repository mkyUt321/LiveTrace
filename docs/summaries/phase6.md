# Phase 6 サマリ: 実験課題の精査と修正

- **日付**: 2026-07-18
- **目的**: Phase 4 の規模スイープが全 N で追跡成功率 1.000 ± 0.000 という不自然な結果を出したことを受け、
  実験設計・評価手法・再現性の3系統を監査し、根本原因を特定して修正する。

## 環境/バージョン
Phase 0〜5 と同一(ns-3-dev 3.48 debug, WSL Ubuntu 24.04, g++13.3, Python 3.12.3, scipy 1.18.0)。

## 監査(3系統・独立)
1. **C++ モデル監査**: 追跡難易度を決める要素が N に依存しているかを精査。
2. **Python 評価手法監査**: `evaluate_phase1/2/3/4.py` と `common.py` の統計処理の妥当性を精査。
3. **ドキュメント・再現性監査**: 各フェーズサマリの自己申告済み限界事項・config との整合・再現可能性を精査。

## 根本原因

### 科学設計:N が追跡難易度を一切駆動していなかった
1. **踏み台連鎖長が固定 `[2,5]`**(N非依存)。観測器は N によらず最大5ホップしか遡らない。← 主因
2. **生きた窓予算も固定**(蓄積2秒+ホップ毎0.6秒 ≒ 5〜6ホップ分)で、連鎖長上限5と偶然一致し
   予算が決して枯渇しない設計になっていた。
3. **固定 p=0.12 のため N が増えるほどグラフが密になり、物理直径がほぼ一定**(旧設定で N=320 でも
   直径≈2〜3)。連鎖長を直径に連動させても、直径自体が伸びなければ意味がない、という隠れた前提破綻。
4. ノードあたり背景ノイズを N 不変(密度一定)に設計していたため、相関の誤検出余地も N で増えなかった。
5. オーバレイ連鎖(攻撃者が選ぶ中継ノードID)が物理直径と完全に非結合だった。

### 評価手法:数値そのものが妥当でなかった
6. `reid_precision` は単一 actor(`attacker.count=1`)では**構造上つねに1.0**
   (全バーストペアが同一 true_actor のため false positive が発生不能)。無意味な自明値だった。
7. **追跡失敗・未応答のバーストが `continue` で分母から除外**され、最悪の失敗(システムが何も
   応答しなかったケース)が評価から消えていた。成功率を過大評価する方向にバイアスがかかっていた。
8. seedあたり約2バーストの平均を(t分布ではなく)正規近似で5seed分平均していたため、
   全seedが2/2成功だとCIが自明に0へ潰れ、"1.000±0.000"のように見えていた。
9. n=5 でも t 分布でなく z=1.96 の正規近似を使っており、CI幅を約30%過小評価していた。

### 再現性
10. Phase 3 の2-actorテストは使い捨て設定(/tmp)で実行されリポジトリに未コミットで再現不能だった。

## 修正内容

### 科学設計(N を難易度に連動)
- **平均次数固定モード**を追加(`topology.avg_degree`、driver で `p = avg_degree/(n-1)` を導出)。
  実測: avg_degree=8 固定で **直径が N=20→3, N=80→4, N=320→5, N=640→6, N=1280→7** と
  対数的に増加することを確認(`contrib/livetrace/model/random-mesh-topology.{h,cc}` に
  `ComputePathStats`(全点対BFS)を追加、`BuildResult` に `diameter`/`avgPathLength` を追加)。
- **連鎖長を実測直径に連動**: `chain_length_factor × diameter`(既定1.2倍、±1ジッター、
  下限2・上限40でクランプ)を `AttackerCampaign::ComputeChainLengthTarget`
  (単体テスト可能な純粋関数として切り出し)で算出するよう変更。N=640(直径6)で目標7ホップとなり、
  窓予算(約5〜6ホップ分)を初めて実質的に超え始める設計になった。
- N=1280 は直径=7まで伸びる兆候を確認したが、1シードの完走に(既定 `default.yaml` 設定でも)
  15分のタイムアウトで打ち切られるほど遅く、繰り返しseedでのスイープからは除外
  (トポロジ特性のみのスポットチェックとして記録)。

### 複数 actor 化・統計的十分性
- 主スイープ用に **`config/scale_sweep.yaml`** を新設・コミット: `attacker.count=2`
  (単一actorでは reid_precision が自明1.0になるため)、周期を420秒→60秒に圧縮し
  `stop_time_s=1200`(20周期、actorあたり約20バースト、周期:バースト比は維持する
  「統計的検出力のための時間圧縮」)。正準420秒は `config/default.yaml` に単一確認点として残す。

### 評価手法
- `analysis/common.py`: `mean_ci95` を正規近似→ **t分布**(`scipy.stats.t`)に修正。
  新規 `wilson_ci(successes, trials)` を追加(二項比率のWilsonスコア区間、非対称)。
- `evaluate_phase1/2/3.py`: 未応答・未マッチのバーストを `continue` で捨てず**失敗として計上**
  (分母を縮めない)。率指標(単ホップ再現率・適合率、追跡成功率、reidのprecision/recall)は
  **全試行をプールしたWilson区間**で報告し、seedあたり平均→CIという二重平均を廃止。
  連続指標(到達段数・time-to-trace・score_gap)はt分布ベースの `mean_ci95` を継続使用。
- `evaluate_phase3.py`: 戻り値を `(precision,recall,n)` から `(tp,fp,fn,n_bursts)` に変更し、
  複数run・複数seedにまたがる正しいプール集計を可能にした。単一actor実行時は
  precisionが自明1.0になる旨をdocstring/出力に明記。
- `evaluate_phase4.py`: 全指標の標本数(試行数/seed数)をCSVに明示的に出力するよう拡張。
- `plot_sweep.py`: 率指標は非対称Wilson区間の誤差棒、連続指標はt分布誤差棒で描画し、
  各点に標本数を注記。

### 再現性
- `config/phase3_reid_test.yaml` を新設・コミット(2-actor再同定テスト、n=20, period=40s,
  stop_time=400s)。Phase3の数値がリポジトリのファイルだけで再現できるようにした。
- `tools/run_sweep_staged.sh` を新設: N≤320 は8seed、N=640 は3seed(実測時間差に基づく段階運用)。

### テスト追加
- C++単体テスト2件: 固定平均次数トポロジの直径が N=200 で非自明な値(>2)になることの確認
  (`Ipv4AddressGenerator::Reset()` が同一プロセス内複数Build()に必要なことも判明・対処)、
  `ComputeChainLengthTarget` の決定的な入出力則(床・天井・単調性)の確認。
- Python単体テスト9件(`tests/test_analysis.py`): Wilson区間の境界・幅の妥当性、t分布CIが
  正規近似より広いことの確認、未応答バーストが正しく失敗計上されることの確認
  (Phase2/Phase3双方)。

## 遭遇した不具合(実装中に発見)
- **ns-3 `Ipv4AddressGenerator` はプロセス全体でグローバルなシングルトン**であり、同一テストバイナリ内で
  `RandomMeshTopology::Build()` を複数回呼ぶとアドレス衝突で `NS_FATAL` が発生する。
  テスト側で `Ipv4AddressGenerator::Reset()` を呼ぶことで解決(本番コード側は1プロセス1回の
  呼び出しのみのため変更不要)。

### 考察

**中心的困難が初めて明確に観測できた。** 追跡成功率は N=20〜40 で 100% を維持した後、
N=80 で 89.4%、N=160 で 62.8%、N=320 で 56.9%、N=640 で 32.5% まで単調に低下する
——まさに「生きた5秒窓で規模の大きいメッシュを起点まで遡り切れるか」という
中心的問いに対する統計的に裏付けられた「否」の領域が、規模スイープとして可視化された。

- **失敗の原因は相関の破綻ではなく時間予算の枯渇**: 単ホップ再現率は N=640 でも一貫して 1.000
  (相関エンジン自体は N が増えてもほぼ完璧に機能し続けている)。一方で窓内到達段数は
  4.98(N=20)→7.00(N=640)、time-to-traceも4.44s→5.71sと単調に増加しており、
  失敗は「相関が間違った候補を選ぶ」のではなく「直径連動で伸びた連鎖の全ホップを
  5秒予算内に遡り切れない」ことに起因すると明確に切り分けられた。これは
  Phase1/2で確認した相関メカニズムの頑健性と矛盾しない、筋の通った結果。
- **平均次数固定によるトポロジ直径の対数的成長**が効いている: N=20→640で直径3→6
  (chain_length_factor=1.2により目標連鎖長 4→7ホップ)。連鎖長の伸びは緩やかだが、
  生きた窓の予算(蓄積2秒+ホップ毎0.6秒 ≒ 5〜6ホップ分)と拮抗する領域に
  ちょうど踏み込んだことで、N=80〜320の間で急激に失敗率が立ち上がる遷移領域が観測された。
- **再同定再現率も N とともに悪化**(0.967→0.548、N=160近辺で底)し、N=640でやや回復(0.629)
  という非単調な挙動を示した。厳密な単調減少ではないが、複数actor・時間圧縮設定下でも
  再同定が N の影響を受けることを示す実データ。N=640での回復は探索的観察に留め、
  今回のセッションでは追加検証しない(標本数が limited なため、今後の課題)。
- **time-to-trace が名目上の5秒予算をわずかに超える**(例: N=640で5.71s)点について:
  これは Python 評価側で `time_to_trace = eval_time_s - burst["start_time_s"]`
  (真の攻撃開始時刻)を用いているため。C++側の `TracebackObserver` 自身は
  `burst_detect_time_s`(victimでの検知時刻、真の開始よりわずかに遅い)を起点に
  厳密に5.0秒予算を守っている。両者の差は起点から victim までの伝播・中継遅延の累積分であり、
  連鎖が長いほど(N が大きいほど)この差が拡大するのは理にかなっている。バグではなく、
  「真の攻撃開始から完全解決までの真のエンドツーエンド時間」というより完全な指標として
  意図的にこの定義を採用している。
