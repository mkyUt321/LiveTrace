# Phase 2 サマリ

- **日付**: 2026-07-18
- **目的**: 生きた5秒窓の中で `TracebackObserver` を再帰させ、起点まで多段に遡上する。
  窓内到達段数と time-to-trace を計測し、起点に届いた場合・届かなかった場合の両方を記録する。

## 環境/バージョン
Phase 0/1 と同一。

## 実装
- `TracebackObserver::AttemptTrace` を再帰化。1ホップ確定(`matched`)すると、
  `Simulator::Schedule(Seconds(hop_delay_s), ...)` で次ホップの相関探索を予約する。
  - `accumulation_delay_s`(既定2.0秒): 最初の相関までの蓄積待ち。
  - `hop_delay_s`(既定0.6秒): 以降の各ホップに追加でかかるコスト。
  - この2つのパラメータにより、**ホップ数と生きた窓の予算が直接トレードオフ**になるよう設計
    (5秒窓・蓄積2秒・ホップ0.6秒 ⇒ 概ね5〜6ホップが窓内で確定できる計算)。これが本プロジェクトの
    中心的困難「5秒の窓の中でどこまで遡れるか」を素朴にシミュレートする土台になる。
  - 既に確定済みノードへの巡回(誤相関によるループ)を検出したら `cycle_detected` で停止。
  - 停止理由は `matched` に加えて `no_match_above_threshold`(真の起点に到達済みで上流フローが
    存在しない場合と、単に相関を見失った場合の両方があり得る。どちらであったかはオラクル照合でのみ判定)、
    `window_expired`、`unknown_peer_address`、`cycle_detected`、`hop_limit_reached`(安全弁、通常到達しない)。
  - 各ホップの結果は同一 `trace_id` で全て `results/traceback_*.jsonl` に記録(システム出力、真値なし)。

## 評価(`analysis/evaluate_phase2.py`)
- 小 N (n=12, p=0.3)、周期40秒・バースト5秒、chain_length 2〜5(既定値)、10 seed × 400秒 = 100バースト。
- **トレース成功率(真の起点に正しい全経路で到達、seed毎平均±95%CI)**: 1.000 ± 0.000 (10 seeds, 100/100 バースト)
- **窓内到達段数(seed毎平均±95%CI)**: 4.610 ± 0.094
- **time-to-trace(成功したもののみ、平均±95%CI)**: 4.219秒 ± 0.134秒(5秒予算のうち)

全100バーストで、victimから起点まで(中継ノードも含め完全一致で)経路が正しく復元された。
例(seed1, burst0): 真連鎖 `[2,5,6,3,8,9,0]`(起点→…→victim)に対し、観測器の復元経路は
`[0,9,8,3,6,5,2]`(victim→…→起点)— 完全一致。

## 考察
- 小 N (n=12) では相関の的中率が非常に高く(Phase1同様)、5秒の窓のうち平均4.2秒を使い切る形で
  ほぼ全バーストが起点まで到達した。これは「小規模では中心的困難がまだ顕在化しない」ことを示しており、
  Phase 4 の規模スイープ(N=数十〜数百)でこの成功率・到達段数・time-to-traceがどう劣化するかが
  本プロジェクトの主結果になる。
- `hop_delay_s` の設計判断(各ホップに固定コストを課す)は恣意的なパラメータであり、実際の
  相関計算に要する「時間」というより「そのホップの証拠が十分蓄積されるまでの待ち時間」の代理である。
  この値の妥当性(何を根拠に0.6秒としたか)は今後、実際の中継遅延・パケット間隔パラメータとの
  整合性を継続的に見直す必要がある。
