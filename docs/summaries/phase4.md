# Phase 4 サマリ

> **【Phase 6 による訂正注記、2026-07-18 追記】**
> 本サマリ末尾の「今後の拡張余地」で挙げた通り、この初回スイープの「全 N で追跡成功率 100%」は
> システムの頑健性を示す結果ではなく、**実験設計上の欠陥**(連鎖長が N に依存しない固定値
> `[2,5]` だったため、固定 p=0.12 のトポロジで N を増やしてもグラフが密になるだけで
> 物理直径がほぼ一定に留まり、踏み台連鎖の深さも生きた窓の予算も一切 N に連動しなかったこと)
> に起因することが Phase 6 の監査で判明した。加えて評価手法にも、失敗バーストが `continue` で
> 分母から除外される・seedあたりの少数バーストを平均してから正規近似CIを取るために信頼区間が
> 自明に0へ潰れる、といった問題があった。詳細な根本原因・修正内容・再測定結果は
> `docs/summaries/phase6.md` を参照。本ページの記述は当時の生の結果として訂正せず残す。

- **日付**: 2026-07-18
- **目的**: ネットワーク規模 N を数十〜数百でスイープし、多シードで4指標
  (time-to-trace・窓内到達段数・追跡成功率・再同定精度)を平均±95%CIで N の関数として測定する。
  これが本プロジェクトの主結果。

## 環境/バージョン
Phase 0〜3 と同一(ns-3-dev 3.48 debug, WSL Ubuntu 24.04, g++13.3, Python 3.12.3)。

## 重要な設計変更(スイープ実行前に発見・修正)

### 1. ルーティングを Global から Nix-Vector に変更(致命的なスケール問題)
既定の `Ipv4GlobalRoutingHelper` は全ノード対の経路を事前計算するため、密なメッシュで
ノード数が増えると極端に遅くなることが判明した。実測(旧ルーティング):
N=20: 2.85秒 / N=80: 15.8秒 / **N=160: 5分超(実行中に強制終了)**。
これは ns-3 で広く知られる Global Routing のスケール限界(数百ノードを超えると事実上使えない)
に一致する。`Ipv4NixVectorHelper`(オンデマンド経路計算+キャッシュ)に切り替えたところ、
N=160 は **45秒**、N=320 は **7分29秒** まで改善し、スイープが現実的な時間で完走できるようになった。
(`contrib/livetrace/model/random-mesh-topology.cc`)

### 2. 背景トラフィックを N に比例させる
当初 `background.rate_pps` はネットワーク全体で固定の集計レートだったため、N が大きくなるほど
ノードあたりの密度が薄まってしまい、「規模が大きいほど雑音が濃くなる」という意図(中心的困難を
N の関数として測る)に反していた。ドライバで `rate_pps × N` にスケールするよう変更し、
ノードあたりの背景密度が N によらずほぼ一定になるようにした(`scratch/livetrace-sim.cc`)。
値は 1ノードあたり 0.05 pps(新規セッション到着率)とし、N=320 でも計算量が過大にならない範囲に調整。

### 3. seed 数を10→5に削減(実測時間に基づく現実的判断)
N=320 は1シードあたり約7分半かかるため、既定の10 seed × 5 N値では約3時間規模になる。
実行可能な時間内に完走させるため、**seed数を5に削減**した(`config/default.yaml`)。
これにより信頼区間はやや広がるが、傾向を掴むには十分なデータが得られた(下記結果参照)。
将来的にさらに多くの計算資源・時間が使える場合は seed 数を戻して再実行することを推奨する。

## 考察(最重要)

**この実験設定(chain_length 2〜5固定、周期420秒・単一攻撃者、N=20〜320)では、
追跡成功率は N=320 まで一貫して 100% に達しており、中心的困難(5秒窓内に起点まで遡り切れるか)は
まだ顕在化していない。** これは失敗ではなく、正直な境界観測である:

- **窓内到達段数**はどの N でも 4.3〜5.0 の範囲で概ね横ばい。これは `chain_length_max=5` が
  N に依存しない固定パラメータであるため — 攻撃者はネットワーク規模によらず短い(2〜5ホップの)
  連鎖を選ぶという仕様上の設計(spec: 攻撃者の連鎖長はNとは独立な軸)の直接的な帰結。
  ホップ数の天井そのものが N でスケールしないため、5秒窓(蓄積2秒+ホップ毎0.6秒 ≒ 5〜6ホップ分の余裕)
  で常に間に合ってしまう。
- **time-to-trace** も 4.0〜4.5秒の範囲でほぼ一定。5秒予算のうち平均で0.5〜1秒程度の余裕を残しており、
  この特定の (蓄積遅延, ホップ遅延, 連鎖長上限) の組み合わせでは、5秒という制約が実質的に
  「効いていない」ことを示唆する。
- 一方で **背景トラフィックを N に比例させ、相関の探索候補プールが N とともに実際に増える**設定に
  したにもかかわらず単一ホップ相関(Phase1由来ロジック)が破綻しなかったことは、
  Zhang–Paxson型 ON/OFF 相関がこの規模・このノイズ密度では十分に頑健であることを示す、
  それ自体価値のある定量的知見。
- **再同定の再現率が N によって大きく振れる(0.6〜1.0)** のは、主に **バースト数がseedあたり
  約2件と少ない**ことに起因するサンプルサイズの問題であり(2バーストが同じクラスタに入るか否かの
  二値的結果が seed 単位でそのまま平均される)、N そのものの効果と区別がつきにくい。
  Phase3 の専用2-actor評価(precision 0.937±0.104, recall 0.833±0.123, seedあたり20バースト)の方が
  再同定メカニズム自体の識別力を測る上ではより有効な評価である。

**今後の拡張余地**(本フェーズでは実施せず、次アクションとして記録):
中心的困難を実際に顕在化させるには、(a) 連鎖長の上限を N に応じて伸ばす、
(b) 生きた窓を5秒より短くする、(c) N をさらに大きくする(数百〜千規模)、
(d) 蓄積遅延・ホップ遅延をより厳しくする、のいずれかが有効と考えられる。
現状は「可能性の地図」の中でまだ易しい領域に留まっていることを示す観測として記録する。
